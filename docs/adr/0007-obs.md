# ADR-0007: OBS

- **Status:** Accepted
- **Date:** 2026-11-08
- **Based on:** StreamWisp ADR-0010 (OBS adapter), ADR-0024 (scene snapshots) and D-110 (OBS controls). The obs-websocket 5 protocol document was re-read on 2026-11-08; the details are in the adapter's manifest (`internal/obs/manifest.go`).

## Context

OBS is where a stream's automation becomes visible: switching to "Be Right Back", showing a clip, muting the mic. OBS runs on the streamer's computer and offers obs-websocket 5, built in since OBS 28. The danger is overriding the streamer: if StreamGremlin switches away for a break and later switches back, it must never undo a scene the streamer chose by hand meanwhile (AGENTS.md's testing invariant).

## Decision

**Connection** (`internal/obs`)
- **Transport:** obs-websocket 5 over `coder/websocket` (the library chat uses), subprotocol `obswebsocket.json`.
- **Handshake:** Hello, then Identify (RPC version 1, SHA-256 challenge authentication), then Identified.
- **Events:** General, Scenes, Inputs, Filters, Outputs, SceneItems and MediaInputs. No high-volume events.
- **Requests** run concurrently, matched by id, with 10 seconds each.
  - If the connection drops after a request was sent, the result is `ErrOutcomeUnknown` (API `unknown_outcome`, 504), never success or failure.
  - If StreamGremlin falls 1024 events behind, the session is dropped and reconnected, never silently thinned.
- **Settings:** the address (default `ws://127.0.0.1:4455`) and the on/off switch are a settings document. The password is the secret `obs/password`. It's write-only through the API, and the CLI reads it from stdin, never from arguments.
- **Reconnecting:** backoff from 1 to 30 seconds with jitter. Three closes stop retrying until the streamer saves the settings again, each with words saying what to do:
  - 4009 (wrong password);
  - 4010 (obs-websocket too old);
  - 4011 (the streamer pressed Kick in OBS; the protocol says not to reconnect on our own).
- **States:** `off`, `connecting`, `connected` (with the OBS and obs-websocket versions and the current scene), `disconnected` (with the reason), and `needs_action`. Only `connected` means StreamGremlin can see OBS.

**Who set the scene**
- Before asking OBS to switch, StreamGremlin records a pending switch: the scene, who asked (`app`, `snapshot:<id>`, later `workflow:<id>`) and when. This happens before sending because the protocol doesn't promise an event arrives after its answer.
- A matching scene-changed event within 10 seconds is attributed to that asker. Any other change is a manual change, and its time is kept.
- **On reconnect**, StreamGremlin compares OBS's scene with the last one seen. A difference is a manual change made while it couldn't see OBS, reported as `broadcast.scene.changed` with `observed_on_reconnect`.

**Events** (source `obs`, `confirmed`, whoever made the change)
- `broadcast.scene.changed {scene_name, scene_uuid, previous_scene_name, changed_by: streamgremlin|external, requested_by?, observed_on_reconnect?}`
- `broadcast.scene_item.visibility_changed {scene_name, scene_item_id, visible}`
- `broadcast.filter.enabled_changed {source_name, filter_name, enabled}`
- `broadcast.audio.mute_changed {source_name, muted}`
- `broadcast.media.started` and `broadcast.media.ended {source_name}`
- `broadcast.stream.started` and `broadcast.stream.stopped`, `broadcast.recording.started`, and `broadcast.recording.stopped {output_path}`. Only the started and stopped states; starting, stopping and reconnecting aren't events.
- `broadcast.replay.saved {path}`

All are in the event catalog, with test events.

**Actions** (Go methods; workflows use them from slice 7). Each needs a live session and fails at once without one: nothing is queued.
- **Reads:** scenes (top first, as OBS shows them), a scene's sources, inputs, and filters.
- **Scenes and sources:** switch scene, and show or hide a source (its first placement). Both set an absolute state, so they're safe to repeat.
- **Filters and audio:** filter and mute take on, off or toggle. Toggle isn't safe to repeat, and says so.
- **Text:** writes only into `text_gdiplus*` or `text_ft2_source*` inputs, at most 16 KiB.
- **Media:** play, pause, stop, restart, next and previous.
- **Recording:** start and stop read the state first and do nothing when it already is.
- **Replay buffer:** save, only while it runs.
- **Screenshot:** into a literal full path. StreamGremlin names the file from the source and the time, so nothing is replaced and chat never picks where OBS writes.
- **Not built:** starting or stopping the stream. It waits for a confirmation design.

**Scene snapshots** (migration `0003_obs_snapshots.sql`)
- **Take:** remembers the current scene under a key (`brb`, or `app` for the app's "Switch for now") and switches, in one step, so ownership is exact.
  - Asking again for the same key and scene while StreamGremlin still holds it reuses the open snapshot, so a second break returns to the scene from before the first.
  - Asking for a different scene under that key is refused.
  - If OBS is already on that scene, nothing switches and restoring does nothing.
- **Restore** switches back only if OBS is connected and its scene is the target, set by this snapshot. Otherwise it's settled as `skipped`, with the reason, and OBS is left alone:

| Reason | When |
|---|---|
| `manual_change` | Someone changed the scene after the snapshot, including away and back, or while StreamGremlin couldn't see OBS |
| `superseded` | StreamGremlin switched again since |
| `ownership_unknown` | Nobody knows who set the current scene |
| `no_switch` | OBS was already on the scene |
| `restarted` | StreamGremlin restarted: ownership was in the old process's memory, so every open snapshot is skipped at start |

- **While OBS is disconnected,** Restore answers "not connected" and the snapshot stays open. Nothing is decided blind.
- **Failures:** a failed switch is `failed` (`switch_failed` or `restore_failed`) and isn't retried. An unknown outcome leaves the snapshot open.
- **Release** stays on the current scene.
- **Records:** settled snapshots never change and are never deleted (triggers). Each settles with `broadcast.scene.restored` or `broadcast.scene.restore_skipped` (source `core`, deduplicated by snapshot).

**API** (permissions `obs.read` and `obs.control`; settings use `connections.write`)
- `PUT /v1/connections/obs`
- `GET /v1/obs/scenes`, `GET /v1/obs/scene-items?scene=`
- `POST /v1/obs/scene`, `PUT /v1/obs/scene-items/visibility`
- `GET`/`POST /v1/obs/snapshots`, `POST /v1/obs/snapshots/{key}/restore|release`

`GET /v1/connections` includes OBS's status and manifest. The other actions have no routes yet: they're workflow steps, and their screen is the workflow editor (slice 9).

**Screen:** Connections → OBS.
- The address and a write-only password, with how to turn on OBS's server.
- The state in words.
- While connected: the scenes, with the live one marked; Switch, and "Switch for now" with "Switch back" or "Stay here"; and each scene's sources, with Show or Hide.

**CLI:** `streamgremlin obs [status | connect | disconnect | scenes | switch | sources | show | hide | snapshot]`.

**Testing without OBS:** `internal/mockobs` and `cmd/mockobs`.
- Scenes, sources, inputs, filters, recording and the replay buffer, in memory.
- Password handshake, and like OBS it sends a request's event before its answer.
- Controls to switch scenes by hand, kick, drop, exit, fail the next request, and start streaming.
- A `/panel` page to switch scenes by hand in standalone use.

## Alternatives considered

- **Raw obs-websocket requests for workflows:** a workflow, Lua or a plugin could then do anything OBS allows (StreamWisp D-110).
- **A separate "snapshot" step before a switch:** it couldn't tell StreamGremlin's own later switch from the streamer's.
- **Restoring after a restart, from a stored owner:** the streamer may have changed scenes while StreamGremlin was closed, and nothing would show it.
- **Retrying requests after an unknown outcome:** each action is safe to repeat except toggles. The caller decides; nothing retries on its own.

## Consequences

- OBS gives no conditional switch, so a manual change in the few milliseconds between the ownership check and the switch back can still be overridden.
- A restore asked for before OBS reports the snapshot's own switch (usually milliseconds) is skipped as `ownership_unknown`, the safe direction.
- Only the program scene counts; studio mode's preview isn't tracked.
